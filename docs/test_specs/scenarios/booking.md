# 予約処理 テスト仕様書 (Booking)

予約処理が要件定義および設計通りに正しく動作することを検証するためのテスト観点とテストシナリオです。

---

## 1. テスト観点一覧

予約処理において検証すべき品質特性と観点です。

| 観点ID | カテゴリ | テスト観点 | 期待される挙動 |
| :--- | :--- | :--- | :--- |
| **TS-B-01** | 正常系 | 残り定員に空きがある状態での新規予約 | 予約が確定し、予約数が+1され、LINE通知が送信されること。 |
| **TS-B-02** | 正常系/UI | 予約処理中の多重送信防止 | ボタンタップ後、処理が完了するまでボタンがDisabledになりスピナーが表示されること。 |
| **TS-B-03** | 異常系 | すでに予約済みのイベントへの再予約 | 重複エラー(422)が返り、予約データが増えないこと。 |
| **TS-B-04** | 異常系 | 満席（予約数＝定員）のイベントへの予約 | 満席エラー(422)が返り、予約データが増えないこと。 |
| **TS-B-05** | 異常系 | 未ログイン状態での予約 | 認証エラー(401)になり、ログイン画面へ誘導されること。 |
| **TS-B-06** | 異常系 | 過去の日時または「終了」ステータスのイベントへの予約 | 期限切れエラー(422)になり、予約できないこと。 |
| **TS-B-07** | 並行処理 | 残り1枠への複数ユーザーによる同時予約 | 1名のみが予約成功し、もう1名は満席エラーとなること。合計予約数が定員を超えないこと。 |

## 2. 具体的なテストシナリオ

### シナリオ 1: 正常予約とLINE通知 (TS-B-01, TS-B-02)
*   **前提条件**:
    *   ユーザーA（LINEログイン済み）が存在する。
    *   イベントX（定員: 10, 現在の予約数: 0）が「公開」状態で存在する。
*   **操作手順**:
    1.  ユーザーAがイベントXの詳細画面から「予約する」ボタンをタップする。
    2.  送信中、ボタンが非活性になりローディング中であることを目視確認する。
*   **期待される結果**:
    *   レスポンスステータス `201 Created` が返る。
    *   `bookings` テーブルに `user_id = A`, `event_id = X`, `status = confirmed` のレコードが1件作成される。
    *   イベントXの現在の予約数が `1` に更新される。
    *   ユーザーAにLINE公式アカウントから「予約完了」のプッシュメッセージが届く。
    *   画面に緑色のトースト「予約が完了しました。」が表示される。

### シナリオ 2: 重複予約の防止 (TS-B-03)
*   **前提条件**:
    *   ユーザーAがイベントXにすでに予約済み（`status: confirmed`）。
*   **操作手順**:
    1.  ユーザーAが再度イベントXの「予約する」API（`POST /api/v1/events/X/bookings`）へリクエストを送信する。
*   **期待される結果**:
    *   レスポンスステータス `422 Unprocessable Entity` が返る。
    *   エラーコードが `duplicate_booking` であること。
    *   `bookings` テーブルのレコード数は増えていないこと。

### シナリオ 3: 満席時の予約不可 (TS-B-04)
*   **前提条件**:
    *   イベントY（定員: 5, 現在の予約数: 5）が存在する。
    *   ユーザーB（未予約）が存在する。
*   **操作手順**:
    1.  ユーザーBがイベントYに対して予約リクエストを送信する。
*   **期待される結果**:
    *   レスポンスステータス `422 Unprocessable Entity` が返る。
    *   エラーコードが `capacity_exceeded` であること。
    *   イベントYの予約レコード数は `5` のままであること。

### シナリオ 4: 同時実行時のアトミック性検証 (TS-B-07)
*   **前提条件**:
    *   イベントZ（定員: 5, 現在の予約数: 4、空き残り枠: 1）が存在する。
    *   ユーザーC, ユーザーD（共に未予約）が存在する。
*   **操作手順**:
    1.  ユーザーCとユーザーDの予約リクエストを、スレッドやテスト用ヘルパーを用いて**ほぼ同時（ミリ秒単位で重なる状態）**に送信する。
*   **期待される結果**:
    *   一方のリクエストが `201 Created`（予約成功）となり、もう一方は `422 Unprocessable Entity`（定員オーバー）となること。
    *   イベントZの最終的な予約数が `5`（定員ぴったり）であり、`6` になっていないこと。
    *   データベースのユニーク制約やロックが正常に機能し、デッドロックでシステムがハングアップしないこと。
