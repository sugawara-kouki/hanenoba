# 設計ドキュメント作成のガイドライン

## 概要
Hanenobaでは、開発者およびAIエージェントが迷いなく設計書を作成・メンテナンスできるように、ドキュメントの配置場所と記述ルールを標準化しています。

## 適用ルール

### 1. ディレクトリ構成の遵守
すべての設計書は `docs/` 配下の定められたディレクトリに配置しなければなりません。

```text
docs/
├── README.md                       # 設計書全体のインデックス（目次・全体案内）
├── system_spec.md                  # ① システム仕様書（全体要件・ER図等）
├── basic_designs/                  # ② 基本設計（外部設計：ユーザー/外部視点）
│   ├── ui_and_transitions.md       # 画面遷移・UI設計（PC/スマホ）
│   ├── line_api_integration.md     # LINE API連携仕様書
│   └── features/                   # 機能ごとの基本設計（1機能＝1ファイル）
│       └── [機能名].md             # 例: booking.md, cancellation.md
├── detailed_designs/               # ③ 詳細設計（内部設計：開発者視点）
│   ├── db_physical_schema.md       # データベース物理設計書
│   └── features/                   # 機能ごとの詳細設計（1機能＝1ファイル）
│       └── [機能名].md             # 例: booking.md
└── test_specs/                     # ④ テスト仕様書（品質保証）
    ├── guideline.md                # テスト方針・RSpec記述ガイドライン
    └── scenarios/                  # 機能ごとのテストシナリオ（1機能＝1ファイル）
        └── [機能名].md             # 例: booking.md
```

### 2. 「1機能＝1ファイル」の原則
機能（例：booking, cancellationなど）ごとにファイルを分割し、各設計カテゴリの `features/` （または `scenarios/`）の下で `[機能名].md` の形式で配置します。
* **ルール**: 1つのファイルの中にそのカテゴリの必要な要素（UI、フロー、API等）を網羅し、過度にディレクトリ階層を深くしないこと。

### 3. 設計書カテゴリごとの記述ルール

* **① システム仕様書 (`system_spec.md`)**:
  * システム全体の目的、機能一覧、全体ER図、開発スタックなど、プロジェクト全体の概要を記述します。
* **② 基本設計書 (外部設計 - `basic_designs/features/[機能名].md`)**:
  * 実装手段（言語のクラス名、DBロック、テストコードなど）を含めず、ユーザーや外部システムから見える「What（何を成し遂げるか）」を記述します。
  * 主な項目: 業務フロー（チェックポイントを網羅したビジネスフロー）、画面の状態変化、LINE連携などの通知仕様。
  * **UI/UX記述の注意点**:
    * スピナーの表示、非活性化（Disabled）、特定のCSSクラス適用など、具体的なフロントエンドの実装手段や技術用語は記述しません。
    * 代わりに、ユーザー目線での「画面状態（State）の変化」（送信中、成功時、失敗時）と、それに対するユーザーへのフィードバック（エラー表示、完了メッセージなど）を抽象的に記述します。
    * 共通のUIパターン（ローディングの標準UI、トーストデザインなど）は `docs/basic_designs/ui_and_transitions.md` に集約し、機能別設計書ではそのルールを前提とすることで重複を防ぎます。
  * **対応するテスト**: **結合テスト（シナリオテスト）**。複数画面の連動や外部API（LINE）との連携が正常に行われるかを検証します。
* **③ 詳細設計書 (内部設計 - `detailed_designs/features/[機能名].md`)**:
  * 実装方法（How）を記述します。
  * 主な項目: クラス・コンポーネント設計（Service Objectの責務など）、トランザクション・排他制御（ロック取得タイミング）、エラーハンドリング。
  * **対応するテスト**: **単体テスト**。クラス単体（Service Object等）やデータベースの制約が個別に正しく動作するかを検証します。
* **④ テスト仕様書 (`test_specs/scenarios/[機能名].md`)**:
  * 品質を保証するために検証すべき正常系・異常系・並行処理などの「テスト観点・シナリオ」を記述します。
  * 基本設計（結合テストレベル）と詳細設計（単体テストレベル）の双方で「何を検証すべきか」の基準となります。具体的なRSpecのテストコード自体はここには書きません。
