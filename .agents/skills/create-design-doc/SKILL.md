# 設計ドキュメント生成・構築スキル

## 概要
Hanenobaプロジェクトにおいて、新規機能の立ち上げや仕様変更を行う際に、定められた構成に沿った基本設計書、詳細設計書、およびテスト仕様書を正しいディレクトリに作成し、全体のインデックスを更新します。

---

## 手順

### 1. 機能名の決定
作成する機能の名前を、英小文字のスネークケース（例: `booking`, `cancellation`, `user_approval`）で決定します。

### 2. 基本設計書の作成
`docs/basic_designs/features/[機能名].md` を作成します。
外部仕様（What）に徹し、データベースロックなどの実装詳細は記述しません。

* **テンプレート**:
  ```markdown
  # [機能名（日本語）] 基本設計書
  
  ## 1. アクターとユースケース
  * **アクター**: 誰が操作するか（例: 一般メンバー、管理者など）
  * **ユースケース**: 何を達成するか
  
  ## 2. チェックポイントと業務フロー
  * ユーザーの要求を受け付ける前にシステムが検証すべきビジネス上のチェックポイントを定義します。
  * Mermaid等を用いたアクティビティ図や状態遷移図で処理の流れを視覚化します。
  
  ## 3. 画面の振る舞いとユーザーへのフィードバック
  * **画面の状態変化**: 処理の送信中、成功時、失敗時の「画面状態（State）の変化」を記述します。スピナーやCSSクラス名などの技術的・具体的な手段は記述せず、ユーザーから見た振る舞いに特化します。
  * **外部連携通知**: 処理完了時に送信される自動通知（LINEプッシュメッセージなど）の有無やタイミング、送信内容を定義します。
  ```

### 3. テスト仕様書の作成
`docs/test_specs/scenarios/[機能名].md` を作成します。
検証すべきシナリオを網羅し、品質を保証するためのテスト観点を定義します。

* **テンプレート**:
  ```markdown
  # [機能名（日本語）] テスト仕様書
  
  ## 1. テスト観点一覧
  * 観点ID, カテゴリ（正常/異常/境界値/並行処理）, テスト観点, 期待される挙動をマトリクス形式で整理。
  
  ## 2. 具体的なテストシナリオ
  * 前提条件、操作手順、期待される結果をステップバイステップで記述します。
  ```

### 4. 詳細設計書の作成（必要に応じて）
`docs/detailed_designs/features/[機能名].md` を作成します。
実装方針（How）について詳細に記述します。

* **テンプレート**:
  ```markdown
  # [機能名（日本語）] 詳細設計書
  
  ## 1. API (エンドポイント) 仕様
  * URL, HTTPメソッド, 認証の有無
  * リクエストパラメータ
  * レスポンス仕様（成功時・エラー時のJSON構造など）

  ## 2. クラス・コンポーネント設計
  * Controller, Service Object, Model, ViewComponentの責務と依存関係の定義。
  
  ## 3. データベース物理設計
  * テーブル構造、インデックス設計、一意性制約、インデックス。
  
  ## 4. トランザクション・排他制御設計
  * 同時リクエスト対策。行ロックなどの制御フロー。
  ```

### 5. インデックスへの追加
* `docs/README.md` を開き、新しく作成したドキュメントへの相対リンクを該当するセクション（基本設計、詳細設計、テスト仕様）に追記します。
