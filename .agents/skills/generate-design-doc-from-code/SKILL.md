# 既存コードからの設計書生成スキル (generate-design-doc-from-code)

## 概要
すでに実装されているRailsソースコードを解析し、プロジェクト共通のドキュメント作成ルール（`documentation-rules`）を**厳守**した基本設計書、詳細設計書、およびテスト仕様書を逆引きで作成・更新します。

---

## 手順

### 1. 対象となる機能と関連ファイルの特定
ドキュメント化したい対象の機能名をスネークケース（例: `cancellation`, `line_login` など）で定義し、その機能に関連するファイルパスをすべて特定します。
*   **Controller**: `app/controllers/...` (APIや画面のエントリーポイント)
*   **Service Object**: `app/services/...` (ビジネストランザクション)
*   **Models**: `app/models/...` (データモデル、バリデーション)
*   **Jobs / Mailers**: `app/jobs/...`, `app/mailers/...` (非同期・外部連携処理)
*   **Specs (テストコード)**: `spec/...` (特にServiceやRequestのRSpec)

### 2. ソースコードの静的解析と仕様の抽出
特定したファイルを読み込み、以下の仕様をコードから抽出します。

1.  **外部仕様の抽出 (基本設計用)**:
    *   認証の要否（セッション確認など）。
    *   どのようなビジネスチェック（バリデーションや条件分岐）が存在するか。
    *   処理の成功時、失敗時（例外発生時）にユーザー側にどのような画面表示・フィードバック・外部通知（LINEなど）が行われるか。
2.  **内部仕様の抽出 (詳細設計用)**:
    *   コントローラーからモデルやサービスが呼び出される順序。
    *   トランザクションの開始・終了範囲、およびデータベースの行ロック（`lock` 等）の取得タイミングと対象。
    *   発生する例外の種類（カスタム例外クラスなど）と、コントローラーでのハンドリング方法。
    *   データベーステーブルのカラム、複合ユニークインデックス、カウンターキャッシュ等の制約。
3.  **テスト観点の抽出 (テスト仕様用)**:
    *   RSpecのテストケース（`context` や `it`）でどのような条件（正常系、異常系、多重リクエストなどの並行処理）をテストしているか。

### 3. 設計ドキュメントの逆引き生成

`.agents/rules/documentation.md` の記述ルールを**厳守**し、以下の3ファイルを生成します。

#### ① 基本設計書 (`docs/basic_designs/features/[機能名].md`)
*   **【厳守】**: スピナー表示やDisabledといったフロントエンドの技術用語、およびクラス名やDBロックなどの実装詳細は一切記述してはなりません。
*   抽出した仕様を元に、ユーザー目線での「画面の状態変化（送信中、成功、失敗）」と、ビジネス上の「チェックポイントと業務フロー（アクティビティ図）」に特化して記述します。

#### ② 詳細設計書 (`docs/detailed_designs/features/[機能名].md`)
*   **【厳守】**: 各パーツ（クラス、DB、例外）を単に列挙する記述は避けてください。
*   **「リクエストが到着してからレスポンスが返るまでの時系列の処理フロー」**に沿って各コンポーネントがどう動くかを詳細に記述しなければなりません。必ずMermaidで時系列フロー（シーケンス図）を作成し、図中のステップ番号に対応する形で、具体的な実装設計（Controller/Service/Modelコード、排他制御、DB物理制約、例外ハンドリング）を記述します。

#### ③ テスト仕様書 (`docs/test_specs/scenarios/[機能名].md`)
*   RSpecでカバーされているテストケースや、ビジネスルール検証の内容から、結合テストレベルで検証すべき「テスト観点マトリクス」と、前提条件・手順・期待される結果を整理した「テストシナリオ」を作成します。

### 4. インデックスへの追加
*   `docs/README.md` を開き、新しく作成したドキュメント（基本設計、詳細設計、テスト仕様書）への相対リンクを追加します。
